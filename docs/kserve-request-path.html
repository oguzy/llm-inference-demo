How a request reaches opt-125m

What happens when you run make kserve-test. One Envoy proxy carries the request. It asks the llm-d scheduler (EPP) which vLLM pod to use, then forwards the request to that pod. The timings come from one real request, x-request-id 29d36b1d….

The pieces

The top row writes configuration before any request arrives. The bottom row handles the request. Only the Envoy proxy, the llm-d EPP and vLLM touch your request.

HTTPRouteopt-125m-kserve-route→ backendInferencePool opt-125m-inference-pool→ endpointPickeropt-125m-epp-service:9002

KServe creates these three objects. Envoy Gateway turns the route into Envoy config. When it reaches the InferencePool backend, it hands off to the AI Gateway controller, which wires in the call to the EPP. The route matches /kserve-demo/opt-125m/v1/completions and rewrites it to /v1/completions.

Things to keep in mind

The EPP never proxies traffic

Envoy sends it the request over gRPC (ext_proc) and gets back one header naming the pod. Envoy then calls vLLM itself.

AI Gateway features are off

Only its controller runs, to support InferencePool. Token rate limits, provider translation and token metrics need an AIGatewayRoute, and KServe creates a plain HTTPRoute.

With one replica there's no real choice

llm-d's scorers still run, but only one pod can win. The 01-llm-d-sim stage runs the same EPP with 2 pods to show real routing.

FailOpen

If the EPP is down, Envoy still sends requests to a pool pod rather than failing them, but without llm-d's routing.

One ID links the hops

Envoy's x-request-id appears in the EPP log and as vLLM's cmpl-… response ID. Envoy's upstream port (52920) matches vLLM's client port.
